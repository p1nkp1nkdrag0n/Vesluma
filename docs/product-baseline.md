## 1. 承接原则与当前定位

以用户较晚的明确说明覆盖早期设想；用户明确决定优先于助手建议。用户说明核心判断已有调研和分析支撑，后续工作据此推进，不把拍照意愿、自由探索、快速开图等既定方向重新列为启动前必须证明的假设。本次未读取调研原始材料，不冒充独立验证其结论。

当前产品定义：一款以地标激活、区域揭雾和旅行记录为核心，支持个人旅行与小队共享的城市探索记录应用。用户选择目标、移动方式和节奏，应用保存定位点、照片与地标激活时间，让单次旅行能够回看，并衔接长期个人地图。

目标用户是有时间、愿意自主探索城市、认可这套记录玩法的旅行个人或小分队。慢逛、快速开图、步行、打车和地铁转场均符合产品设定。

当前项目目录采用 Vesluma，本文件以此作为工作名称。历史对话未出现用户最终确认该名称的独立回复；不把工作名称写成已经完成品牌定稿。

## 2. 已明确的核心规则

下表依据历史中两轮用户关于闭环和规则的直接表达，以及本轮用户批注确认整理。

| 编号 | 已明确的决定 | 后续设计含义 |
|---|---|---|
| C01 | 应用主要负责旅行记录与自主探索，提供基础读图和方位辅助 | 用户可通过真实主干道简图选择道路；MVP 不新增自动最优路线或逐路口指令 |
| C02 | 交通站点是优先的旅行开篇，也可从其他地标开始 | 机场、火车站可提供抵达与合影场景，不形成唯一必经入口 |
| C03 | 到访地标、合影上传、完成激活并展开区域 | 合影与旅行记录结合，保留地标激活时间 |
| C04 | 使用持续请求的位置进行基本激活校验 | 采用用户自愿遵守玩法的前提，不为蓄意绕过规则建设专门反作弊体系 |
| C05 | 未解锁区域显示真实主干道简图，隐藏详细底图、支路与街巷 | 以最少信息帮助用户判断城市通路；手绘只改变显示样式，地标和实际点仍可见 |
| C06 | 地图支持放大缩小，用户自主判断与行动 | 不因用户绕路、走远或改变目的地而纠偏 |
| C07 | 指南针持续指向用户选中的下一个地标 | 配合主干道简图进行基础读图；无需为查看基础路网离开应用，复杂导航及交通服务仍可交给其他应用 |
| C08 | 动态、定时采集位置，速度影响采样安排 | 具体合理间隔需在工程中确定；未解锁区域内也持续记录 |
| C09 | 只保留并显示定位点，以点云观察经过 | 用户已修正早期“点连成线”表述，不把足迹画成连续路线 |
| C10 | 支持个人和旅游小队，小队信息同步到成员账号 | 小队旅行有共同记录，也允许成员临时脱离小队自主游览 |
| C11 | 小队在地标打卡只上传一次 | 不要求同一合影先转发、再由每个成员重复上传 |
| C12 | 上传进入个人或团队云空间 | 云端保存本身不等于向所有人公开 |
| C13 | 用户可选择向其他人展示打卡并同步关联位置 | 其他用户能在地图相应位置查看人们如何打卡；公开是主动选择 |
| C14 | 解锁边界依据道路、河流等现实结构划分 | 需要真实现场调研和地标信息核实，不能用地标周围固定半径圆代替 |
| C15 | 最终能够激活整座城市的全部地图 | 城市区划应支撑完整覆盖；具体城市和地理范围仍待落地配置 |
| C16 | 体验价值包括未知带来的好奇、揭雾成就感、时间与内容回看 | 需要保存开图事件、旅行定位点与照片，不能只做一次揭雾动画 |
| C17 | 慢慢探索与快速解锁都被允许 | 不以旅行速度或是否乘车判定玩法是否正确 |
| C18 | 地标由近及远展示 | 用户澄清此前“由远及近”为口误；地图仍保持真实地理位置 |
| C19 | 开图进度永久保留 | 旅行结束后进度继续存在；本轮已确认 |
| C20 | 重访不重置 | 再次来到已展开区域不会恢复迷雾；本轮已确认 |
| C21 | MVP 测试城市采用南京和西安 | 同一产品承载两座城市的测试内容 |
| C22 | C 纸感地图作为主方向，藏宝图作为可选主题 | 主题只作用于未解锁简图；共用真实道路数据，不改变权益或玩法 |
| C23 | 已展开区域保持真实详细底图与真实路网配置 | 不用生成插画、手绘街区或主题滤镜替代；激活和换主题后真实地理关系保持一致 |

用户本轮要求将持续定位的范围留到后续解决。定位生命周期、开启与暂停、旅行外采样和后台策略均暂缓决策，不把先前助手的“仅旅行期间”解释作为已定规则。MVP 设计仍保留实际位置点记录和基本位置校验的产品要求。

### 本轮澄清与确认

用户已明确澄清：正确方向为“由近及远”，此前“由远及近”为口误。该歧义现已消除；具体控件仍由 MVP 设计落实。

开图进度永久保留、重访不重置已从历史建议升级为用户确认。用户要求进一步解释“首次激活与后续到访分别保存”，尚未确认其完整交互；解释与建议见 [MVP 设计](mvp-design.md)。

本轮用户将“未解锁区完全不可见”调整为“真实主干道的手绘简图”，以最少信息辅助自主探索；用户偏好 C 纸感地图，并接受藏宝图作为可选方向。随后明确补充：已经开启的地图必须保持真实路网配置。因此，最新规则为未解锁区显示主题化主干道骨架、已解锁区显示真实详细地图。概念图仅为未解锁显示风格参考，不能把其中生成的已展开街区作为真实地图数据。

## 3. 已形成的整体体验框架

抵达城市或选择一个起始地标 → 开启个人或小队旅行 → 到访合影并提交 → 基本位置校验 → 保存照片和激活时间、展开对应区域 → 查看其他地标并选定目标 → 指南针指向目标、用户自行移动 → 持续保存位置点 → 再次激活 → 回看照片、点集与开图过程 → 积累长期旅行记录。

这是对已明确机制的整合，不意味着已经选定每一步的页面、按钮和先后限制。

产品中有四种不同的状态需要在设计中表达清楚：

- 地标激活：某个地标何时发生过一次打卡事件。
- 区域展开：某片地图的详细底图是否可见。
- 实际足迹：设备采集到的位置点及时间。
- 内容共享：照片和事件由谁保存、哪些人可查看。

这种分离是历史助手提出的实现框架，与用户机制相容；具体数据表和权限规则尚未定稿。区域展开不应被解释成区域内每一处都已有个人足迹。地图展开前后使用同一批已采集位置点，背景从主干道简图切换为真实详细底图。主干道在激活前后保持同一真实位置与连通关系；看见骨架本身不构成激活或到访。

### 地图的基本状态

| 内容 | 未解锁区域 | 已解锁区域 |
|---|---|---|
| 真实主干道与必要路名 | 可见，以纸感／藏宝图样式显示 | 可见，沿用真实详细底图 |
| 支路、街巷、建筑与普通 POI | 隐藏 | 按真实地图与缩放级别可见 |
| 主要水域与方位参照 | 可按真实轮廓简化展示 | 按真实详细底图显示 |
| 纸感／藏宝图主题 | 只改变简图笔触、纸色等显示 | 不覆盖或替代真实底图与路网 |
| 待激活地标位置 | 可展示 | 可展示 |
| 本人已采集位置点 | 继续记录和显示 | 继续记录和显示 |
| 当前目标与指南针 | 可使用 | 可使用 |

历史助手还建议在两种区域中查看地标介绍、照片与公开打卡，并规定查看公开内容不改变个人解锁状态。这些属于后续交互设计参考，尚不是用户逐项确认的显示矩阵。

### 小队的基本关系

已明确的是共同记录、一次上传、同步到成员账号，以及临时独行。历史助手建议照片和事件复用同一份内容、每人设备分别记录自己的点集、共同地图与个人足迹分开管理。这有助于避免把别人的位置点误写为自己的位置点，但具体同步对象、权限及独行期间规则仍需在创建过程中细化。

## 4. 可以承接的功能与页面草案

以下是原助手整理出的功能结构，可用于开始设计；不是已经批准的导航栏或首版范围。

| 功能入口 | 主要职责 |
|---|---|
| 城市探索地图 | 迷雾、已解锁底图、地标、足迹点、当前目标和指南针 |
| 地标详情与打卡 | 地标介绍、目标选择、照片提交、激活时间、相关打卡内容 |
| 当前旅行 | 记录状态、个人或小队模式、旅行开始与结束、同步状态 |
| 小队空间 | 成员、共同内容、独行与会合、共享相册和权限 |
| 旅行回顾 | 通过地图、时间轴和相册查看同一次旅行 |
| 我的地图 | 跨城市、跨旅行的记录与长期积累 |
| 城市内容管理 | 地标档案、现实区划、激活关联和城市覆盖维护 |

公开打卡可以先依附地图与地标页面呈现；独立信息流、点赞、排行榜和等级系统并未定案。

后续创建时，应让一个可体验的流程真实覆盖“到访—激活—区域揭雾—迷雾中留点—回看”。只实现普通地图或静态宣传页，无法代表已经讨论的核心产品。

## 5. 城市内容与地理数据

现场核实地标、按道路和河流等现实边界划区、最终支持全城开图，是用户明确要求。因此，地图内容制作与应用开发同样属于产品落地工作。

历史助手提出了以下可采用的数据组织方向：

- 城市范围：定义该城市完整地图的地理边界。
- 区域：按真实地理结构形成可展开的多边形。
- 地标：名称、位置、介绍、可到访及拍照地点等资料。
- 激活关联：规定一次地标激活会展开哪些区域。
- 到场范围：用于基本位置校验；与地图展开边界分别配置。
- 主干道骨架：从真实路网筛选主干道与必要路名，核实交汇、桥梁及通行属性，与真实详细底图使用一致坐标；主题不改真实几何。
- 覆盖维护：检查区域间空缺、入口关系和地标变化。

正式内容需来自实际核实。未来若使用演示城市、示意区划或模拟位置，应明确标记，不能把演示数据说成已经完成现场调研。

## 7. 已被后续说明覆盖的旧方向

| 早期观点或助手建议 | 当前承接方式 |
|---|---|
| 路口语音解释、转向引导、结束探索时内置导航 | 当前主定位已明确为记录，方向辅助采用目标指南针；旧能力不列为当前必做项 |
| 未解锁区域显示完整路网，或完全隐藏全部道路 | 最新规则为保留真实主干道简图、隐藏支路与详细底图；激活后展开真实详细地图 |
| 纸感或藏宝图覆盖整个城市，已展开区也用生成街区 | 主题只作用于未展开简图；已展开地图保留真实底图与路网，概念图不作为地理配置 |
| 走到哪里就沿足迹消雾 | 核心开图由地标激活整块现实区划，足迹另行记录 |
| 定位点连成连续路线 | 用户已明确改成点云，不连线 |
| 快速赶地标属于产品失败或违背探索 | 用户明确允许快速开图，旅行节奏由用户决定 |
| 怀疑照片来源而扩展身份或照片鉴伪 | 用户明确认为基本位置校验足够，不为蓄意作弊扩展系统 |
| 交通站点必须是唯一入口 | 站点是优先展示的典型开篇，其他地标同样可以开始 |
| 上传照片即公开到社区 | 上传进入个人或团队云空间，公开由用户选择 |
| 小队同一合影需要每人上传或逐人重复确认 | 一人提交一次即可，不恢复重复操作负担 |
| 固定半径圆作为最终解锁区划 | 使用道路、河流等现实边界并实地核实 |
| 把已有产品判断全部恢复为待验证假设 | 按用户明确的产品前提开展创建，工程和内容细节另行细化 |

Vesluma 是原助手首选。其造词方案为 ves（取自 vestigium）＋ lum（取自 lumen）＋ a（读音结尾），品牌意象是让到访的地方逐渐明亮，让经历留下痕迹。它是创造的品牌词，不是古拉丁语现成单词。

原建议品牌表达：

> Vesluma<br>
> Uncover the city. Keep the memories.<br>
> 展开一座城，留下这一程。

读音、中文音译和口号尚未由用户定稿；地图视觉已明确采用 C 纸感为主方向、藏宝图可选，见 C22、C23。历史中的普通网页初查不构成商标、域名或应用商店名称已经可用的结论。
