## 本轮发现及处理

1. 原方案首次缓存全部城市。改为按需缓存及城市上限，补旧缓存迁移、回访顺序和配额失败回滚。
2. 首次地图早于 worker 接管、旧 worker 更新窗口可能错过保存。加入协议握手及交接；地图显示不等待缓存。
3. HTTP 200 可能是坏地图，HTTP 缓存也可能保留坏响应。校验失败不保存，自动解压响应去除旧编码头。初次浏览器执行发现三个离线场景失败：外链网络拦截使普通地图请求的 HTTP cache mode 变为 `reload`，原逻辑因而跳过已有有效地图；无拦截的对照正常。现仅明确的 `X-Vesluma-Map-Retry: 1` 表示应用重试并绕过地图缓存，同时保留 HTTP `cache: reload` 更新坏响应。33 项 worker 和 18 项加载器检查通过，真实浏览器两模式对照均命中缓存；最终完整应用中，坏 HTTP 200 两次被拒绝、恢复真实响应后在线及离线刷新均通过。故障代理响应设置 `Cache-Control: public,max-age=600`，证据中的 `no-cache` 是请求头；测试路由会禁用 HTTP 缓存，因此不把此场景当作长期 HTTP 缓存毒化实测，显式跳过旧缓存另有单元契约检查。见[诊断证据](acceptance/gba-2026-10-02/sw-cache-mode-diagnosis.json)。
4. 广州解压响应超过原单地图 50 MiB 保护值。改为有限的 64 MiB 并验证边界。
5. 修复合法空海片误判、边界刷新收据过期、香港首次导入缺区界发现步骤；隔离临时目录演练未联网或刷新冻结来源。
6. 原成都生成配置两段文字与发布 JSON 有漂移。生成器恢复发布文本，使旧六城对象哈希一致；未改旧点位或权益。

## 仍需用户或现场验证

浏览器模拟和两个独立 context 仅用于本地工程验证，不代表真实手机、实地抵达或实际跨设备联网。SQLite 测试仅使用临时数据库，固定测试空间不提供正式身份认证；未开通云服务、收费服务、凭据或部署。

首次安装耗时、低端手机内存、发热、系统存储配额、真实弱网、GPS／相机及后台行为需要用户设备验证。原生资源未同步，未编译、签名 APK／IPA。

所有新点仍标为候选。250 米数值范围不能证明跨水面或受管制区域可达。普通妈阁庙点距来源边界约 205.7 米，需特别校准到场位置；一级代表此次局部平面筛查最小边距约 319.1 米，也不替代测绘和通行核验。公众地点的票务、预约、施工与开放时间可能变化。深圳深汕及港澳源几何是游戏覆盖，不据此推断行政归属或通行许可；源面积不是官方陆地面积。
